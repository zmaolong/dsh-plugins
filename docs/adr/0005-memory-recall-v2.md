# 0005 记忆召回 v2：会话首步快照注入 + 分层索引 + 按需读取

- 状态：已采纳
- 日期：2026-11-10
- 背景：preview.5 起记忆索引注册为 `systemPrompt.context`，每个 model step 都重新渲染；条目上限全局/项目各 50 条、总 12,000 字符；检索为子串匹配 + 字段权重累加；工具契约为「search 先取 limit 再过滤 type」（已知 bug）、「get 最多 10 条 / 8,000 字符」；注入行只有名称与截断描述，没有 id 与类型，模型无法稳定地按需取全文。
- 现状事实：宿主 `dsh-agent-loop` 每个 model step 用 `session.deriveMessages()` 重建整份请求；`RuntimeContextProjection.project()` 只在渲染内容与保留快照不同时追加新快照，压缩替换后会自动重新追加（宿主源码 `dsh-agent-loop/lib/index.js:205-349`、`dsh-system-prompt/lib/index.js:141`）。宿主 `LlmAdapter` 无 embedding（`listModels/resolveModel/prepareCall/stream` 之外没有 `embed`），因此 ADR-0001「不做向量库」的结论继续成立。

## 决策

1. **会话首步一次**：记忆索引按会话渲染一次并缓存（`sessionId → 渲染字符串`），之后每个 model step 返回同一字符串。宿主按内容差异去重，不会重复追加；压缩导致旧快照被替换后，宿主投影会自动重新追加同一快照。面板提供「刷新索引」显式失效缓存。
2. **分层注入**：全局块只放 `preference`/`decision`，项目块只放 `gotcha`/`project`；每层 10–20 条（常量可调），总字符预算约 3,000；超限追加截断提示。全局在前、项目在后，按 importance、updatedAt 排序。
3. **索引行格式**：`id · 类型 · 名称 · 80 字描述 · 重要性`。
4. **工具契约**：
   - `memory_search` 返回摘要行（id、类型、名称、一句话、更新时间），并明确提示「拿到 id 后用 `memory_get` 取全文」；`type`/`status` 过滤下推到存储层，`query` 允许为空（返回排名索引）。
   - `memory_get` 单次最多 3 条、总输出 4,000 字符；超出时明确返回「已截断，请再取下一批」。
5. **不投入检索算法升级**：不做 BM25、语义重排或 LLM 精排；只修「过滤在 limit 之后」「空 query 契约」等 bug。
6. **提示词分工**：`MEMORY_GUIDE` 只保留极短的「何时用记忆」，不复述 `AGENTS.md` 的策略话术（静态人写规则 vs 动态提炼事实）。

## 理由

- 宿主虽然每个 step 重建请求，但 runtime-context 快照只在内容变化时追加；因此「每步重算」没有 token 收益，反而增加重算与装配期副作用（项目身份解析会写 `config.json` 与 `.git/info/exclude`）。
- 会话首次加载的索引足够：模型自己写入的记忆它已经知道；其他来源的新记忆靠 `memory_search`/`memory_get` 按需获取。刷新索引反而会在历史里追加多份索引副本并破坏前缀缓存。
- 宿主没有 embedding，检索排序的可提升空间有限；把投资转给「索引可被引用 + 全文按需读取」的两段式路径，单位收益更高。

## 放弃的方案

- **每步/每轮刷新索引**：历史中会累积多份索引副本、从追加点之后的前缀缓存失效，收益接近零。
- **零条目开场注入**：模型不会主动搜索，等于放弃召回。
- **BM25 / 语义重排 / 向量缓存**：宿主无 embedding；插件零运行时依赖。
- **在注入里塞全文**：上下文预算不可控，且与「按需读取」工具重复。

## 后果

- 「命中率」指标废弃，改为两个口径：**注入利用率**（会话内被工具回读的注入条目 ÷ 注入条目）与**检索命中率**（检索结果被 `memory_get` 打开的比例）。
- 会话内索引与记忆库可能短暂不一致，以工具结果为准；面板提供刷新入口。
- 压缩后重注入依赖宿主 runtime-context 投影行为（pre-stable），每次宿主升级必须回归。
