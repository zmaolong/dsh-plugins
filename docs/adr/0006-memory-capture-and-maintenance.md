# 0006 捕获与维护 v2：模型主动写入 + 会话末补漏；维护 Run 手动触发、两阶段研判

- 状态：已采纳，轮末自动提炼部分取代 [ADR-0002](0002-memory-capture-gate.md)
- 日期：2026-11-10
- 背景：ADR-0002 的轮末自动提炼每轮触发一次额外模型请求，且 `force` 关键词扫描跨轮缓冲（400 事件）导致「说一次记住」后每轮都过闸门，成本被持续放大；误记没有事后撤销入口；记忆体检只能逐条给建议，无法做跨条目的合并与清理。用户在 2026-11-10 共识中确认：**鼓励多写 + 定期合并删减 + 利用率指标**，并接受维护先手动触发。

## 决策

1. **捕获入口改为模型主动**：模型通过 `memory_save` 主动写（严格模式：先 `memory_search` 查重，仅在用户显式要求、或出现稳定偏好/决策/坑/项目事实且无重复时保存）。取消轮末自动提炼；会话结束（`agent/disposed`）执行**一次**批量补漏提炼，受 `captureSessionEnd` 开关控制。
2. **捕获可撤销**：面板「最近捕获」列表 + 单条撤销；不做完整待审箱。
3. **维护 v1 为手动触发**：面板「优化记忆」按钮；进入面板时若达阈值（新增/强化累计 ≥30 条，或距上次维护 ≥7 天）弹窗提示用户触发。自动触发留后续版本。
4. **维护实现为 LLM 研判流水线**：规则预筛候选（重复对、低利用率条目）→ 分批发给模型输出结构化计划（合并 / 停用 / 恢复 / 删除）→ 插件按硬规则校验后执行。**不是真子代理**：宿主 `ctx.subagents.startActivation` 要求 `request.parent` 是活着的 Agent，插件加载时无法启动。
5. **范围与预算**：每次 Run 处理全局 + 一个项目（按最久未维护轮转，当前项目优先）；候选 ≤200 条、总输入 ≤40k token；独立「维护模型」设置，默认继承最近会话模型。
6. **两阶段研判**：
   - 首次研判：`usedCount = 0` 且距 `updatedAt` ≥90 天且 `importance < 60` → 置 `stale`（不注入，仍可检索）。
   - 再次研判：≥7 天后仍未被使用 → 删除或恢复 `active`，由模型研判决定。
   - 安全网：`pinned`、`importance ≥ 80`、被 `supersedes` 引用的条目不自动删除；删除前写入 `memory/trash/<日期>.md`（保留 30 天）；每次 Run 写入维护流水，可整次撤销。
7. **保留两票制**：`memory_forget`/`/forget`/`supersedes` 仍先标记 `stale`；归档与删除由维护 Run 或用户在面板执行，模型工具不再输出「再调一次就归档」的诱导文案。

## 理由

- 轮末每次模型请求是固定成本，而多数轮次没有可长期复用的事实；模型主动写 + 会话末一次补漏把成本压到每会话 ≤1 次。
- 自用场景下「多写 + 定期整理」比「少写 + 严格审查」更不容易漏记；合并与清理需要跨条目判断，规则引擎做不了，LLM 研判可以做但不该拥有不可逆权限。
- 手动触发让成本与时机可控，先验证研判质量再考虑自动化。

## 放弃的方案

- **轮末自动提炼（ADR-0002 原方案）**：成本不可控且有 force 泄漏。
- **捕获待审箱**：自用低频维护，事后撤销足够。
- **真子代理维护**：父 Agent 依赖、不可离线测试、预算难约束。
- **自动删除且无备份**：不可逆操作不可接受。
- **首次研判即删除**：借鉴两票制的审计窗口。

## 后果

- 每条记忆需要利用率字段（见 [ADR-0007](0007-memory-schema-v2.md)），维护 Run 依赖它做低价值判定。
- 面板需要「优化记忆」入口、阈值提示、最近捕获、维护流水与撤销、trash 恢复；分属 B2/B3/B4 批次。
- 维护质量取决于研判提示词与规则预筛；阈值写成常量，跑一个月后再调。
- 会话末补漏仍在 `agent/disposed` 用同一个模型调用，失败静默重试一次。
